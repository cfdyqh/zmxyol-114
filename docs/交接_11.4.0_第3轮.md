## 一、抓包链路（已验证可复现）

```sh
adb reverse tcp:8443 tcp:8443
su -c 'sysctl -w net.ipv4.conf.all.route_localnet=1'
# 信任库 bind mount（重启失效）：把 v11/certs/c5d7d7c3.0 放进 /data/local/tmp/cac
su -c 'mount --bind /data/local/tmp/cac /system/etc/security/cacerts'
uid=$(dumpsys package com.zmxyol.union.uc | sed -n 's/.*userId=\([0-9]*\).*/\1/p' | head -1)
su -c "iptables -t mangle -A OUTPUT -p tcp -m owner --uid-owner $uid --dport 443 -j MARK --set-xmark 0x0/0xffffffff"
su -c "iptables -t nat    -A OUTPUT -p tcp -m owner --uid-owner $uid --dport 443 -j REDIRECT --to-ports 8443"
python v11/mitsrv.py          # 记完整请求；YJ_HANG=1 可挂住连接不回应
```

要点：**mangle 里把 fwmark 清 0 是必须的**，否则 REDIRECT 到 127.0.0.1 的包会被
per-uid 路由又扔回原网卡（第 2 轮卡在这里）。客户端完全信任自签 CA。

抓到的（每次启动/点「重试」都会发一次，**密文每次完全一致** → 无随机 IV）：

```
GET  http<path>   ← TP2
POST http<path>                                   ← 更新检查
     Content-Type: application/json, Content-Length: 1364
     -=4399=-eDMSfv6/7Fb3e8hCNqbhOJvMqBD6K2xvimIzAJWVkejJcsHANaJGoSz3rVykJ... (base64)
```

`-=4399=-` / `*=4399=*` / `*#%4399*` 三个标记在运行时解密后的字符串池里（.rodata），
对应不同报文类型。base64 字母表在 libgame 里（`ABCDEFGHIJKLMNOPQRSTUVWXYZ...+/`）。

## 二、请求明文（从进程内存里挖出来的真身）

用 /proc/PID/mem 全量 dump + 搜索，拿到了 checkupdate 的 JSON 明文片段
（完整片段见 `v11/cu_plain_fragment.txt`，760 字节）：

```json
...,"md5":"0f5427d1ce3c35f24160bfdb28da94ce","pid":"5",
"safe":"3d039681396e58b175bbc89674a2c551","uuid":"64D8CD29FC6B5BEF7F21E4AEA5F7998A",
"action":"checkupdate","apk_dir":"/data/user/0/com.zmxyol.union.uc","channel":108,
"service":-1,"version":"s11.4.0","gametime":0,"dataversion":"11.4.0",

"yj-libgame":"4ac023775162719e6e0f8d2d2914762d",          ← libgame.so 的 MD5

```

**重要**：客户端会把 `sensitivefiles` 里各文件的 MD5 上报（libgame 的 md5 就是原包那个

## 三、加密算法定位：AES（不是 DES）

libgame 静态链了整份 OpenSSL（`DES_set_key_unchecked`/`DES_encrypt1`/`AES_encrypt`/
`base64Decode` 都是导出符号，见 `v11/_got.py` / `_finddes.py`）。

做法：用 root 直接改**运行中进程**的内存（libgame 的 .text 因为是加密壳，映射是 `rw-p`，
所以 `/proc/PID/mem` 可写！），把各个密文函数的入口写成 `bx lr`（`0x4770`），重启客户端
再抓包对比：

| 被 nop 的函数 | 抓到的 body |
|---|---|
| `DES_encrypt1` | 与原来完全一致 |
| `DES_encrypt2` | 完全一致 |
| `DES_ncbc_encrypt` | 完全一致 |
| `DES_ede3_cbc_encrypt` | 完全一致 |
| `DES_encrypt3` | 完全一致 |
| **`AES_encrypt`** | **请求根本没发出去（客户端在发送线程里挂了）** |

→ **request 的加密走 AES**。注意密文长度 1016 字节不是 16 的倍数（1016 = 8×127），
所以不是 AES-ECB/CBC，而更像 **AES-CTR / AES-CFB**（流式，长度任意；`CRYPTO_ctr128_encrypt`、
`CRYPTO_cfb128_encrypt` 也都在导出符号里）。密文每次一致 → IV/key 都是固定的。

## 四、下一步（已经非常具体，按顺序做）

1. **恢复 keystream（最省事，不需要 key）**
   - 先拿到**完整**的请求明文 + 对应密文。
   - 若是 CTR/CFB（keystream 与明文无关、每次从 0 开始），则
     `keystream = 密文 XOR 明文`，**直接用同一段 keystream 就能造任意应答**（长度 ≤ 1016）。
   - 拿完整明文的两条路：
     a. 内存快照：JSON 在 `[anon:libc_malloc]` 区（本轮两次都落在这个 11 MB 区，
        例：`ceb80000-cf680000`），用 `v11/native/scanmem2.c`（已编译、已推到
        `/data/local/tmp/scanmem2`）**只扫这个区循环抓**（一次 ~10 ms），
        边点「重试」边抓（`v11/loopscan.sh`）。
     b. 或者把 `AES_encrypt` 改成 `out=in` 的桩（16 字节 copy），让 keystream 变成
        counter 块（通常大半是 0），密文就基本等于明文了。
2. **拿到 key/IV 也可以**：`AES_encrypt(const uchar *in, uchar *out, const AES_KEY *key)`
   —— 在 libgame 的 rw .text 里写一个 ARM 桩，把 `out`（=keystream 块）和 `key->rd_key`
   抄到一块固定 scratch，然后从 /proc/pid/mem 读回来。桩要放在 .text 的空隙里，
   入口用 `b.w` 跳到桩、桩里先执行被覆盖的原指令再跳回。
3. 有了 keystream/key 之后：
   - 先造一个「更新检查通过」的应答（格式参照 v800/v411 的 `LocalServer.java`/`Canned`，
     `{"code":0,...}` 那一套），看客户端下一步要什么（登录/选服）。
   - 直接对同一个客户端**录制-回放**：把真实服务器的应答密文抓下来（把 mitsrv 改成
     **透传代理**，转发到真服务器并记录双向字节），回放给客户端 —— 这样连协议明文都不用懂。
     注意真服务器会回「请勿使用破解版」，所以只能用它验证链路，不能用来过关。
4. 并行：仍可继续 de-乐固路线的 exit(15)（第 2 轮 §2.4 的 seccomp 验证没拿到干净结果）。

## 四之二、AES key 抓取尝试失败：houdini 不执行注入的 ARM 代码

想直接在进程里 hook `AES_set_encrypt_key` 把 key 抄出来，做了完整的 trampoline：

1. 目标：libgame 的 **真实实现** 在 file VA `0x1a54eec`（导出的 `AES_set_encrypt_key`
   `0x1a54ea4` 只是个 3 条指令的 thunk：`push {r3,lr}; bl 0x1a54eec; pop {r3,pc}`，
   内部调用不走 thunk，所以要改真实实现）。
2. 它的前 8 字节是固定的 `push {r4,r5,r6,r7,lr}; mov r7,fp; mov r6,sl; mov r5,sb`，
   可以整个换成跳板；桩里先重放这 4 条，再 `ldmia r0` 抄 16 字节 userKey，最后跳回 `real+8`。
3. 桩放在 .bss / .text（覆盖没用的 `SEED_encrypt`）都试过；跳板试过 `ldr.w pc,[pc,#0]`
   和 **装配器算好的 `b.w`**（用 `.org` 把真实距离 0xC434 喂给汇编器，见 `v11/_mk_hook.py`）。

结果：**只要 AES_set_encrypt_key 被调用，进程立刻 `SIGILL`，崩在 `libhoudini.so`**：

```
signal 4 (SIGILL), code 0 (SI_USER)
backtrace: #00 pc 002786bf /system/lib/libhoudini.so
```

结论：**houdini 翻译不了/不允许执行我们自己写进 guest 内存的代码**（哪怕写在已经
被执行过的 .text 页里）。所以「在进程内注入 ARM 桩」这条路基本死了，**必须走纯数据路线**：
内存扫描拿 key/keystream（见 §四.1），或者改 *数据*（GOT/全局变量），不要改 *代码*。
