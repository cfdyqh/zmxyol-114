法宝物品 JSON 形状（照存档里能用的 500018 抄的）：

```json
{"A2":ID,"A4":1,"A5":实例id,"A6":1,
 "A7":生命,"A8":魔法,"A9":攻击,"AA":防御,
 "AB":400,"AN":1,"AO":4,"AQ":13,"AT":0,
 "AV":10,"AW":500,"B8":0,
 "BG":[5个孔位],"CD":0,"CE":27,"CG":0,"CV":100,
 "D2":0,"D3":1,"D4":0,"D5":0}
```

- **`BG`/`BW` 不要手写**：`BW` 是客户端自己生成并维护的孔位数组，删掉或改成 5 个全解锁都会 **SIGSEGV**。
- 孔数由表决定，靠重建物品让客户端重掷。

### 4.2 法宝五行编码

`AN=1` → 底色固定 **金**；`AO` 是**组合序号**（不是位掩码）：

| AO | 显示 |
|---|---|
| 3 | 金 水 木 |
| 4 | 金 火 |
| 5 | 金 土 |

实测其它组合：`(AN=2,AO=0)`=金、`(3,1)`=水金、`(3,2)`=火土、`(3,4)`=水木、`(4,1)`=火火、`(4,2)`=火金。
**`AN`≥5 或 `AN=4,AO`≥3 会 SIGSEGV**（超出组合表）。

### 4.3 客户端逆向要点

- libgame `.text` 是 XOR 0xB5，`v11\native\libgame_plain.so` 是解密版，VA == 文件偏移，Ghidra image base 0x10000
- ARM32 PIC 用 `ldr rX,[pc,#imm]` + `add rX,pc,rX`（相对池）
- 客户端 JSON 是 **jsoncpp**，类型枚举 `0=null,1=int,2=uint,3=real,4=string,5=bool,6=array,7=object`
- `v11\_findrefs2.py` / `_callers.py` / `_dis.py` 是 ARM+Thumb 引用扫描工具

**应答结构（已逆清）**
`prayequips: [ {globalitemid, saved?, unsaved?} ]`

`_parsePrayEquip @0xf8125c`：
```
r4 = "saved"
if (elem.isMember("saved"))        goto 0xf815c0     // saved 分支
r4 = "unsaved"
if (elem.isMember("unsaved"))      goto 0xf81658     // unsaved 分支
return
```
- **两个分支互斥，`saved` 优先**。以前同时发 `"saved":{}`，`isMember` 为真 → `unsaved` 永远被跳过。
- 分支里都要求值是 **jsoncpp object（type 7）或 null（type 0）**，数组会被丢（`0xe7403c`）
- 且要求 **非空**（`0xe73ef0` 返回 1 表示空 → 直接 return）
- 通过后执行 `manager[0x198]->vtable[0x28](saved)` 和 `manager[0x1a0]->vtable[0x28](unsaved)`，
  即**只把对象存进两个 manager**，不直接刷 UI
- 键名 `p` / `v` / `l`（`0x1c336c8` / `d0` / `d8`），另有 `unsaved_10`（`0x1c336e0`）

**已试过（全部无效）**

| 应答 | 结果 |
|---|---|
| `{saved:{}, unsaved:{}}` | 无反应（走了 saved 分支且为空） |
| `{saved:{}, unsaved:{"unsaved_1":[{p,v,l}]}}` | 无反应 |
| `{saved:{}, unsaved:[{p,v,l}×5]}` | 无反应（数组被类型检查丢） |

| 去掉 `saved`，`unsaved:{p:0,v:5000,l:1}` | 面板数值仍不变 |

## 1. 「每次登录等级变 1」的根因与修法

**根因**：客户端会拿角色列表（`roles.json` 里的 `rolelv`）去**同步存档**。
我们的 `rolelist` 一直返回 1（或硬写 90），客户端就把存档压成那个值。

**修法**：`ensurePresetRoles()` 里改成每次登录**从各自的存档文件读真实等级**，
写回 roles.json 的 rolelv/rolelevel。官服（8.0/16.9）就是这么做的——rolelist 反映存档真实等级。

**教训**：不要把 `rolelv` 硬写成常数（无论 1 还是 90），否则每次登录都会覆盖玩家进度。

## 1. 暴击伤害 ≈ 0（已修）

**根因（客户端计算问题，不是属性问题）**

`YJRoleBullet` 命中后的暴击分支在 `libgame` 里是这样的（ARM，VA 0x13e9c4c）：

```
13e9c4c  add r0, r6, #0x590    ; A = bullet.critFactor
13e9c50  add r0, r0, #4
13e9c54  bl  0x65768c          ; 读 A
13e9c58  mov r1, r0
13e9c5c  mov r0, r4
13e9c60  bl  0x1aa06fc         ; r4 = damage * A  (__aeabi_fmul)
13e9c64  mov r1, #0
13e9c68  mov r4, r0
13e9c6c  bl  0x1aa0adc
13e9c70  cmp r0, #0
13e9c74  beq 0x13e9248
13e9c78  ...                   ; + B
13e9c94  b   0x13e9248
```

A / B 来自角色聚合出来的 `critical_damage`（`YJRole::getCriticalDamage` @0x13480bc，
它把各个属性来源对象 `+0xa4` 的浮点加起来）。本机这个和是 0，于是
**暴击伤害 = 普通伤害 × 0 ≈ 0**（面板里「暴伤 0」就是这个值）。

**为什么不能直接改 .so**

`libgame` 会校验自己的 .text：只要 `libgame.so` 有一个字节和原版不同，
启动就弹「更新检查失败, 请勿使用破解版进行游戏(3)」或者直接 SIGSEGV
（实测：把 .text 末尾 4 字节改成 NOP 也一样崩）。所以文件必须保持逐字节原样。

**修法：运行时内存补丁（改 libtprt 垫片）**

`native/tprt_shim.c` 本来就是我们自己写的壳（替掉乐固 libtprt），它已经有
`libgame_base()` + `mprotect` + 全内存扫描的 urlpatch 线程。这轮给它加了一个
`patch_crit_damage()`：等 libgame 加载完，把上面那段尾巴改写成

```
ldr r1,[pc,#12] ; 1.5f
mov r0,r4
bl  __aeabi_fmul
mov r4,r0
b   0x13e9248
.word 1.5f
```

也就是 **暴击 = 普通伤害 × 1.5**。改倍率只要跑
`python _mk_shim_crit.py 2.0`（1.5/1.75/2.0 都行）再重打包。

- 生成脚本：`v11\_mk_shim_crit.py`（注入 + 用 NDK r26 编译成 `native/libtprt-crit.so`）
- 打进包里的位置：`lib/armeabi/libtprt.so`

## 4. 孙悟空被动吸血（已打补丁，待战斗复测）

**定位**：命中时唯一真正加血的地方在 `libgame` 0x13e32c8：

```
13e32c8  bl 0x13efef8        ; rate = attacker->attr(0x80)  <- bloodSuckingRate
13e32cc  mov r1, r0
13e32d0  mov r0, fp          ; fp = 本次伤害
13e32d4  bl __aeabi_fmul     ; sb = 伤害 * rate
13e32e8  beq ...             ; <=0 直接跳过
13e32f0  blx r6              ; heal(target, sb, 1, 0)
```

`attr(0x80)` 就是 JSON 里的 `bloodSuckingRate`（键名在 0x1c37b68，
序列化在 0x132e070），本机是 **0** -> 既不会过判定也不会回血。
roll 判定那处（0x13e31a4 ~ 0x13e31ac，`随机 < rate`）读的也是同一个值。

**做法**：和暴击一样在 `libtprt` 垫片里做内存补丁（`patch_lifesteal()`），
把两处的 rate 都写成 `0.05f`（`movw/movt`，0x3D4CCCCD）：

- 0x13e31a4: `mov r3,#0` -> `movw sb,#0xCCCD`；0x13e31a8 -> `movt sb,#0x3D4C`；
  0x13e31ac -> `mov r0,sb`
- 0x13e32c8: `bl 0x13efef8` -> `movw r1,#0xCCCD`；0x13e32cc -> `movt r1,#0x3D4C`

生效标记：`/sdcard/yj/lifesteal_ok`。
**注意**：这是「每次命中回 5% 伤害」的效果，不再走随机判定；
如果实测觉得太强，把常量 0x3D4CCCCD 换成更小的浮点即可（改 `_mk_shim_crit.py`）。

### 1.5 诛仙剑阵继承

- 面板文字：`注：剑阵将继承嵌入法宝属性的%d%%`（字符串 @ `0x1c163a8`）；
- 计算代码 @ `0xca6554`–`0xca6598`：

```
0xca6554  bl 0x7f0348          ; 单例
0xca6564  blx [vtable+0x198]   ; A = 某对象（float）
0xca657c  bl 0x68f4ec(3,1,0,0) ; B = 配置值（应为 50）
0xca658c  bl __aeabi_fmul      ; A × B
0xca6590  bl __aeabi_f2iz      ; → int
0xca6594  format("%d%%")
```

即 **percent = A × 50%**，A 是客户端算的“已嵌入比例”。

- 存档实证（客户端自己上传的 33KB 档）：
  - 四把剑在背包：`500016/509338`、`500015/509339`、`500014/509340`、`500013/509341`；
  - 剑阵 `A5=509342`：`AN=4`，`BW[0..3]` 全部 `BX=1` 且 `C1` 指向四把剑（**镶嵌是落盘的**）；
  - `A7..AA = 508/260/323/177` —— 服务端 `applySwordArrayInherit()` 已按每把 50% 算好写进物品；
  - 但面板仍显示 0%。

- 结论：**A 的来源不是 `BW` 槽位**，客户端还有另一个“继承比例”的输入（很可能来自服务端的某个应答字段，或 `noblest_enhance` 类配置）。

### 1.6 Frida 在这台模拟器上不可用（重要，别再试）

- frida-server 17.26.2 android-x86_64 能跑（root），`frida-ps` 能列出进程、能 attach；
- 但 **`Interceptor.attach` 一挂到 `libgame.so` 的代码上，进对应界面就 SIGSEGV**（剑阵面板复现两次）；
  原因：houdini 把 ARM 翻译成 x86 执行，Interceptor 要改写目标指令，翻译层不容忍；
- 另外 **frida 枚举不到 `libgame.so`**（houdini 下模块列表里看不到），
  base 只能从我们垫片的日志里拿：`logcat | grep "libgame.so+"` → `base=0x311c000`。

> 结论：要做运行时埋点，只能用**我们自己的 libtprt 垫片**，不能用 Frida。

## 2. 下一步（垫片埋点的设计方案）

目标：抓到 `0xca658c` 那条 `fmul` 的两个乘数（A 和 50%），从而确定 A 从哪来。

现成条件：
- 垫片里已有 `libgame_base()`、`mprotect`、写入后 `__builtin___clear_cache` 的成熟流程；
- 已成功改过 `0x13e9c4c`（暴击）和 `0x13e31a4`（吸血），机制稳定。

难点：`0xca658c` 附近 **±1MB 内没有 0x00/0xFF 的空洞**（我扫过，0 个），
所以不能像暴击那样就地塞常量，需要：

1. 在垫片里找一块**可写可执行的自有内存**（mmap 一块 RWX），
2. 把 `0xca658c` 的 `bl __aeabi_fmul`（`0xEB...`）替换成 `bl <我们的桩>`——**但 BL 只有 ±32MB**，
   垫片的 mmap 地址未必落在范围内；更稳的做法是把桩写进 **libgame 自己 .text 里一处已知的
   “死代码”**（要找），或者用 `ldr pc, [pc, #-4]` + 绝对地址的 8 字节 trampoline（需要 16 字节空间）。
3. 桩里先 `str r0,[scratch]; str r1,[scratch+4]`，再 `bl __aeabi_fmul`，再 `bx lr`；
4. 垫片后台线程每秒读 `scratch`，变化时追加写 `/sdcard/yj/trace.txt`。

另一个更省事的方案（推荐先试这个）：
- **直接改 A 的值看面板反应**。把 `0xca6588`（`mov r0, r5`）改成 `mov r0, #` 一个常量 float 寄存器来源，
  或者把 `0xca657c` 的配置调用改成固定值 50（`0xca6578 mov r0,#3` → `mov r0,#<other>`），
  看面板数字怎么变，反推 A 的取值来源。

- 物品 `A2` 不是 `500026`（诛仙剑阵不能问仙），且 `AV >= 10`。
- 当前档里的五件：四把 10 阶传说剑 `500013/14/15/16` + 万仟花篮 `500018`。
- 新获得的 10 阶传说装备在下一次登录/存盘时自动补上。

## 2. 峰值数值（10 阶）

| 属性 | 峰值 | 写到哪里 |
|---|---|---|
| 生命 | +10000 | 物品 `A7` |
| 魔法 | +5000 | 物品 `A8` |
| 攻击 | +1000 | 物品 `A9` |
| 防御 | +500 | 物品 `AA` |

| 豁免 | +3630 | 物品 `saved` + 角色 `attribute`（仅装备后） |

## 3. 实现（`LocalServer.java`）

- `applyPeakPray(store)`：读档和存盘上传后各调用一次。
  - `yj_peak[gid]` 记每件物品的**原始 A7..AA**，每次都用
    `原始值 + 峰值` 重算，客户端反复上传也不会越叠越高。
  - 同时给物品写 `saved`（只放暴击/闪避/魔抗/神力/豁免五条，四维已在 A7..AA，避免双倍）和 `BO=1`；
    并写 `yj_pray[gid] = {degree:10, saved:<峰值>}`，
    这样 `savedata.prayequips` 里也会带 `equip_pray_attr -> saved`，
    客户端如果在载入阶段解析问仙属性，九条都能拿到。
  - 穿在身上的 10 阶装备（`A6=1`）才把暴击/闪避/魔抗/神力/豁免
    累加进 `roledata.role.attribute`；百分比按原有量纲加
    （原值是 0.16 这种小数就加 0.09，是 9 这种百分点就加 9）。
- `buildSavedataBlock()` 先把状态写回 `store` 再拷贝给客户端，
  避免「下载时叠一次、上传后再叠一次」的双倍加成（fix206 就踩过）。
- 关闭开关：`touch /sdcard/yj/no_peak`，重启游戏后不再叠峰值。

## 9. fix246：背包扩充「发生不可预知的错误」

**现象**：点背包扩充，客户端弹「发生不可预知的错误」。

**根因**：`buybagprice` 落进了通用 `fillBuy`，应答是

```json
{"point":100000000,"goods":{"A2":503036,"A4":99,...},"goodsId":503036}
```

客户端要的是 `point + price`（price 是物品对象），拿到 `goods/goodsId` 解析失败。

**修法**（参考 `v55/out55` 的 5.5 离线版）：

```
buybagprice -> {code:1000, point:<当前点券>, price:{A2:503037, A4:<价格>, B7:0}}
buybag      -> 扣点券 -> {code:1000, point:<新点券>, price:{...}, bagsize:<新格子数>}
```

- 价格取 `assets/database/bag_size_price.sdb` 的 `price_list[index]`；
  请求里的 `index` 就是当前格子数，`price_list[58] = 140`。
- 货币物品是 **503037 点券**（不是 503036 随机制作书）。
- `buybag` 扣点券、把 `bag.bagsize` 至少推到 `index+1`，并落盘。
- 兼容别名 `REQUEST_BAG_OPEN_PRICE` / `REQUEST_BAG_OPEN`。

包：`v11\build\fix246.apk`（716,441,374 B，基于 fix245 只换 classes2.dex，

# 2026-11-13 23:3x · fix256：至尊传承（对照 13.0 私服的官方还原实现）

**详细说明见 `v11\至尊传承_修复说明_fix256.md`**，这里只记结论与后续。

参考：`zmxy130-server`（13.0.3）的 `_noblest_inherit_do`，它是按官方
`noblest_inherit.pyc` 反汇编逐行还原的（用户实测「至尊传承正常」）。

## 根因（四处，全部有证据）

1. **传承挂接没实现**：`handleAction` 只认 `4/5/6/9/7/8/10`。官方挂接是 `27`；
   11.4 客户端自己的 `logs` 里写着 `"54":[{"M":{"A2":1311,"A5":1311},"T":{...}}]`
   → 11.4 用的是 **54**。两者现在都处理。
   `CD`/`CQ` 不落库 → 传承槽永远空 → 「属性传承比例」恒 0.0%。
2. **`CV` 语义写反**：官服 `CV=100` 是「传承等级上限」；旧代码每次锻升 `CV=CE`，
   `normalizeNoblestInherit` 也这么写 → 锻升一级上限就塌到当前等级，下一次立刻「已到上限」。
3. **锻升不扣料**：客户端 `material[].A4` 是它自己的显示计数（恒 0），旧代码 `need=A4*steps=0`。
   官方费用在 `extreme_cnf`：规则 5（CE<100，熔炼丹 503206 + 仙气 503035）、
   规则 9（CE≥100，熔炼丹 + 元灵精魄 503199）；仙气扣 `bag.auracount`。
4. **聚炼只写 `CV=100`**：官方是 `CL=now+10800`、`CM=0`、`CE<100` 才可用、生效中拒绝续用。

连带修掉：升品把品阶镜像写进 `CL`（`CL` 现在是聚炼时间戳）；锻升的属性加成被外层
`applyNoblestStats` 抹掉；传承族跳过老 `material[]` 扣料（否则挂接会把传承装备 `A4` 减到 0）。
