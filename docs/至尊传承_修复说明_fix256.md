## 一、结论：不是一处 bug，是四处

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | **传承挂接（inlay）根本没实现** | `handleAction` 只认 type `4/5/6/9/7/8/10`；官方 `noblest_inherit` 的挂接是 `27`（13.0），而 11.4 客户端自己的 `logs` 里带着 `"54":[{"M":{"A2":1311,"A5":1311,…},"T":{…}}]` | `CD`（传承槽指向的源装备）/`CQ` 永远不落库 → 槽位空 → **面板「属性传承比例」恒 0.0%** |
| 2 | **`CV` 语义写反了** | 存档实证：所有装备 `CV=100`（官服这是「传承等级上限」）；旧代码每次锻升都写 `CV = CE`，`normalizeNoblestInherit` 也这么写 | 锻升一级上限就压到当前等级 → **下一次锻升立刻「已到上限」** |
| 3 | **锻升不扣材料** | 客户端 `material:[{A2:503206,"A4":0},{A2:503035,"A4":0}]` 里的 `A4` 是它自己的显示计数；旧代码 `need = A4 * steps` = 0 | 免费锻升，且与官方消耗不符（熔炼丹 + 仙气） |
| 4 | **聚炼只写了 `CV=100`** | 官方 `noblest_inherit` type=9：`CE<100` 才可用、`CL=到期时间戳`、`CM=0` 表示生效中、扣聚炼丹 503212 | 界面不倒计时、「临时 100 级」不生效；重复点也不会被拒 |

另外两个连带修掉的：

- **升品把品阶镜像写进 `CL`** —— `CL` 现在是聚炼到期时间戳，写品阶会把聚炼状态冲掉，
  读档时还会把时间戳当成品阶。已去掉该镜像（客户端读的是 `CF`，这一条早就验证过）。
- **锻升的属性加成被外层 `applyNoblestStats` 抹掉** —— 分支里刚叠完「传承装备 × 等级%」，
  外层又按表重算一遍四维，白叠。已让锻升跳过外层重算。

## 二、改动（`v11\java\org\yjmobile\zmxy\offline\LocalServer.java`）

### 2.1 `handleAction` 新增/重写三个分支

**type 6 锻升（官方 cultivate）**

```
CE + 1，上限 = CV（官服恒 100，缺省也按 100）
消耗 = extreme_cnf 规则 5（CE<100）或规则 9（CE≥100）：
   熔炼丹 503206  = trunc(0.05×lv² + 6.5×lv − 1)        lv = CE+1
   仙气   503035  = trunc(9.5×lv² + 45.5×lv + 451) 按 10 取整   ← 扣 bag.auracount，不是背包物品
   CE≥100 时第二样换成 元灵精魄 503199 = trunc(1×lv² + 5×lv − 8000)
材料不够 → result=0 + 「材料不足：熔炼丹×N、仙气×M」，不扣料、不加等级
```

**type 9 聚炼（官方 concentrate）**

```
CE ≥ 100 → 「该装备传承等级达到聚炼丹效果上限，无法使用」
CM==0 且 CL > now → 「当前聚炼尚未结束」
扣 聚炼丹 503212 × 1；CL = now + 10800（180 分钟）、CM = 0、CV = 100
```

**type 27 / 54 传承挂接（官方 inlay）**

```
target.CD = 源装备 A5；源装备.CG = target.A5；同时给一份 CQ 快照（源装备副本，CG 指向 target）
应答额外带 update_cg / target_item / add_goods / remove_goods / source_uid
源装备 A5 的取值顺序：source → source_uid/inherit_uid/inlay_uid/src → target.CD
                     → logs["54"]/["27"][].M.A5   ← 11.4 客户端实测就记在这里
                     → material[] 里第一件带 A5 的装备
```

应答形状：`info:{result,msg,titletip,update,cost}` + 顶层 `operation / uid / before / after /
expires / duration / update_cg / target_item / add_goods / remove_goods`（官方形状）。

### 2.2 配套

- `equipJson()` 给新发的至尊装备补 `CV=100 / CL=0 / CM=1 / CU=0 / CW=0`（以前没 `CV`，
  客户端可能当成 0 → 锻升直接判上限）。
- `normalizeNoblestInherit()`：`CV` 强制 100；补 `CL/CM` 默认值；**不再**往 `CQ` 上写
  `CE/CV`（那会把源装备的传承等级改掉）；`CD>0` 但 `CQ` 丢了的老档，按 `CD` 把源装备
  快照重建回来（面板才有「传递值」可比）。
- 传承族（6/9/27/54）跳过老的 `material[]` 扣料逻辑 —— 否则挂接时客户端把传承装备塞进
  `material`（A4=1），老逻辑会 `findStack` 命中那件装备并把 `A4` 减到 0，装备会消失。

# fix257：诊断版（比例还是 0 时用这个）

产物：`out\造梦西游OL-11.4-离线版-fix257.apk`（716,445,470 B，同签名，覆盖安装保档）

## 结论先说：比例 0 的两个充分原因

1. **传承等级 = 0**。存档实证（`$tmp\dev114\savedata_base.json`，用户 11-13 19:14 上传）：
   两件至尊 `500223 / 500224` 都是 `CE=0`。面板「传承等级：0级」→「属性传承比例：0.0%」是必然结果。
   游戏内规则表（`noblest` rule 71000003，见 13.0 的 `noblest_catalog.json`）原文：
   > 通过**锻升**可以提高传承等级，**传承等级越高，属性传递的比例越高**。

   所以要先锻升（fix256 起锻升按官方扣 熔炼丹 503206 + 仙气 503035，包里现成各 9999 / 1e8）。
2. **传承槽里没有传承装备**。同一份规则原文：
   > **传说和魂器品质的装备**，可以作为传承装备放入至尊装备中。传承装备的属性将以一定的比例传递给继承装备。

   只有放了传说/魂器，客户端才会算「传递值 / 原有值」，比例才有意义。
   用户包里可用的魂器：`1311 御龙棍`、`3510 盘龙铠`（`equip.sdb` grade 6）。

## 本轮新增（只影响日志与兼容，不改变数值逻辑）

- `HANDLEACTION done type=… A5=… CE=… CV=… CD=… CQ=0/1 CL=… CM=… result=…`
  —— 每次至尊操作后打一行，直接看出字段有没有落库。
- `NOBLEST-upload …` / `NOBLEST-serve …`
  —— 每次存档上传 / 下发，把每件至尊的 `CE/CV/CD/CG/CQ/CF/CC/CL/CM` 汇总成一行（最多 8 件）。
- 兼容 13.0 的 action 名：`noblest` / `noblest_*` / `inlay` / `inheritequip` /
  `extremestunt*` / `extremebaptize*` 也走 `handleAction`（缺 `type` 时按有无 `source` 判断）。

## 我漏掉的东西

13.0 的 `mock_server_v2.py` 第 6601 行起有一条明确写着「★ 2026-11-12 至尊修复」的代码：

```python
# ★ 2026-11-12 至尊修复：extremeCnf 是官方 roledata2 **响应顶层**下发的服务器
#   规则表（tool_extract fixtures dd671c79 实证 PATH=/response/extremeCnf,
#   action=roledata2）。缺了它 → 至尊升品/升星 UI 费用显示 0、确认时客户端
#   读空配置弹「存档已损坏」
if action == "roledata2":
    o.setdefault("extremeCnf", _sys_load("extreme_cnf.json"))
```

也就是说：**至尊那一整套面板（升品/升星/锻升/聚炼/传承）的费用与比例，都要读 roledata2
顶层下发的 `extremeCnf` 规则表**。11.4 服务端从来没发过这条 —— 之前几轮只补了
`slot_stunt_*`，漏了 `extremeCnf`，所以「属性传承比例」一直是 0.0%。

官服 roledata2 fixture（`work\device\sdb\official169_roledata2_fixture.json`，
133 个顶层键）里 `extremeCnf` 的原文已经整段抄进 `LocalServer.EXTREME_CNF_JSON`
（850 字节，10 条规则，与 13.0 的 `extreme_cnf.json` 逐字一致）。

1. `EXTREME_CNF_JSON` + `extremeCnf()`：官方 `extremeCnf` 规则表（规则 1 升品、
