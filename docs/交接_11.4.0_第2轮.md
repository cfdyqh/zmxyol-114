# 造梦西游OL 11.4.0 · 第二轮结论（2026-11-06 下午）

> 接 `v11/交接_11.4.0.md`。这一轮的净收获是**把 libgame.so 的加密解开了、
> 把 exit(15) 排除到只剩两个方向**，并且确认了一条绕开反外挂的旁路（原包 + 本地服）。
> 设备当前装的是**原版 11.4.0**（`/data/local/tmp/orig.apk` 也在）。

---

## 一、最重要的一条：libgame.so 其实只是 XOR 0xB5

用 `base(2).apk` 里的 `libgame.so` 和运行时 dump 重建的 `v11/native/libgame_dec.so`
逐字节对比：

| 范围 | 结论 |
|---|---|
| `.text` 段（文件 0x5e4d30 .. 0x1aa3bb3，21.75 MB） | **整段与 0xB5 异或**，单一固定 key |
| 其余所有段 | 明文，与 dump 一致 |

验证：`python v11/patch_libgame_xor.py --src v11/libgame.so --out x.so --decrypt-only`
解出来的镜像与 `libgame_dec.so` 在 21243 个采样点上 **0 差异**，首字节
`45 f5 98 5c` → `f0 40 2d e9`（`push {r4,r5,r6,r7,r8,r9,r10,r11,lr}`）。

### 运行时谁解密、什么时候

`libtprt.so`（libgame 的 DT_NEEDED）在**加载时**就把 `.text` 原地解开了，
和乐固的 Java 壳没关系。证据（de-乐固包，用 `v11/native/tersafe2_trap.c` 里的探针）：

```
libgame .text 映射：036fc000-04bbc000 rw-p  off=0x5e4000   ← 注意是 rw-，不是 r-x
t+500ms 读 0x36fcd30：f0 40 2d e9 04 c0 91 e5 ...          ← 已经是明文
```

（r-x 位置只有第一段 `r--p`；ARM 代码由 houdini 从内存翻译，不需要 PROT_EXEC，
所以乐固可以把它映射成可写再解密。）

### 所以我们终于能改 libgame 了

```
python v11/patch_libgame_xor.py --src v11/libgame.so --out v11/native/libgame_p.so \
        --script my_patch.py      # my_patch.py 里定义 patch(data: bytearray)
# 再把结果塞进包： cycle.ps1 -Game 'native\libgame_p.so'
```
脚本会自动「解密 → 打补丁 → 重新加密」，段头/其它段一个字节都不动。

> 注意：改完 **不要**把明文版直接放进 APK（libtprt 会再异或一次，变成乱码）。

## 二、exit(15) 到底是谁：排除法结果

### 2.1 已经排除：不是 guest 侧 libc 的 exit 调用

`tersafe2_trap.c` 把所有能想到的终止入口都在 **guest libc** 里做了 inline hook
（`exit/_exit/_Exit/abort/raise/kill/tgkill/pthread_kill/pthread_exit/__stack_chk_fail/__assert2/__android_log_assert`），
并用 `kill(getpid(),0)` 自测证明 hook 是**真的生效**：

```
I/YJOffline: hook: exit @0xb630290 -> 0xb91a308        （13 个全部成功）
I/YJOffline: EXIT-HOOK kill(7449,0) lr=0xb91a0e8       ← 自测命中，说明补丁是活的
```

之后进程仍然 `exited cleanly (15)`，**一个 hook 都没触发**。
→ exit 不走 guest libc 的任何入口。也不是 libgame 里的裸 `svc`：
libgame 的明文 `.text` 里 18 个 `svc`，没有一个是 `exit/exit_group`。

### 2.2 已经证实：这个包有反调试，`strace`/`ptrace` 一律会被反杀

用 `strace -f -i -e trace=exit_group` attach 后，进程不是退 15，而是：

```
[pid 8764] [eed2fb08] exit_group(4)
```
`eed2fb08` 在 houdini 的翻译区，说明**是 guest 代码里的裸 svc**，
而且是被 TracerPid 之类的检测触发的，退出码 4。

> 这也解释了之前所有 strace 观测为什么都是噪声（3 次 SEGV、exit(4)），
> 以及为什么 `SEGV_ACCERR 0xcb34d9c` 那种现场没有参考价值。
> **以后不要再对这个包用 strace/ptrace/gdbserver。**

### 2.3 libtprt.so 是「杀手」的主要嫌疑，也是目前最可控的靶子

libtprt（158 KB，file VA，Ghidra 要 +0x10000）：

| 项 | 值 |
|---|---|
| 导出 | 只有 `JNI_OnLoad @0x326c`、`unwind_xx_tpshell_crcI/II/III`、数据 `g_tprt_pfn_array @0x24d00`、`g_tprt_ori_array @0x27c4c` |
| 手写 `exit_group` 裸 svc（movs r7,#0xf8; svc #0） | `0x2bd4 0x2eb8 0x331e 0x4522 0x5414 0x738e 0x85b0 0x8988 0xcdf8 0xdf8a 0x11d74`（其中 0x451c/0x7386 两个是 `exit_group(r0)` 动态码） |
| 关键字符串 | `g11FileChecker`、`ch_tprt_mem`、`/proc/%u/cmdline`、`/data/data/%s/files/comm.dat`、`/sdcard/sdk/shell.log` |
| 其它 | `TPShellApplication` 的 native 方法名**不在 .rodata**（JNI_OnLoad 里注册的名字是混淆/运行时解密的），所以静态找不到 `initialize` |

实测：**把这 11 个 svc 全部 nop 掉（`v11/_nokill.py`），进程反而死得更早**
（libgame 还没 load，200 ms 后就 `exited cleanly (25)`）→ libtprt 在**构造函数阶段
就有一层自校验**，我们改它的字节会被它发现。

这也解释了交接文档里「改 libtprt → exit(2)」：就是同一层自校验。

### 2.4 现在的三条线索（按性价比）

1. **`TprtBoot` 那条路是死路**：反射调 `initialize()` 之后进程 1.4 s 内
   `exit(4)`（= 乐固的「文件被改」码），说明 initialize 会去校验 dex/manifest/so，
   我们改过的 manifest 必然过不了。
2. **exit(15) 出现在 `nativeInit` 之后 ~40 ms**，且与 TP2 无关（原版 TP2 / stub 都退 15），
   与 libgame 明文执行无关。最可能是 libgame 通过 `g_tprt_pfn_array[]`
   调到 libtprt 里某个「未初始化就报错」的路径，或者 libtprt 的另一处裸 svc。
3. **还没试的干净做法：seccomp 把 exit/exit_group 变成 ERRNO(0)**，
   让「退出」变成「继续跑」，再用 `kill -3` 让 ART 把线程栈打出来。
   `v11/native/seccomp_block.c` 已经写好并成功编译，第一次测试**无效**——
   原因是当时 `hook_syscall()` 把所有 `syscall()` 都吞掉了（返回 0 没转发），
   所以 `syscall(__NR_seccomp,...)` 是假成功；这个 bug 已修（hook 列表里删掉 `syscall`），
   但修复后的那次构建进程启动就崩了，**还没拿到干净结果**，这是下一步第一件事。

## 三、旁路方案（强烈建议并行推进）：原包 + 本地服（root）

这一轮最大的意外收获：**原版 APK 在模拟器上完全跑得起来**，
卡住的地方只有「更新检查」——它停在 `正在检查更新中...`，弹「更新…是否…」，
进程一直活着（pid 存活、GL 线程正常、`cocos2d-x debug info` 一直输出）。

也就是说：**只要我们能替服务器回答，就不需要碰任何反外挂。**
这条路完全绕开乐固/TP2/exit(15)，也不需要改 APK。

### 已搭好的地基

| 组件 | 状态 |
|---|---|
| CA + 服务器证书（SAN 覆盖 `zmol/zmxychatxm/zmxyworldbossxm.4399sj.com`） | ✅ `v11/mk_certs.py` → `v11/certs/` |
| 设备信任库注入：bind mount 覆盖 `/system/etc/security/cacerts` | ✅ 已生效（138 条，含 `c5d7d7c3.0`）；重启失效，需重做 |
| 本地 TLS 服务器（记录完整请求 + 可配置应答） | ✅ `v11/mitsrv.py`（PC 侧，`adb reverse` 进来） |
| 把设备的 443 引到本机 | ⚠️ iptables `REDIRECT --to-ports 8443` 计数能涨（5 包/300 B），但包**没有**到达 adbd 的 `127.0.0.1:8443` 监听——Android 的 per-uid fwmark 路由把重定向后的包又扔回原网卡了 |

### 下一步（按顺序）

1. 修重定向：在 `mangle` 表给该 uid 的包清 mark（`-j MARK --set-xmark 0x0`），
   或在设备里跑本地服（不放 PC），或用 `ip rule` 把 fwmark 的包引到 lo。
   `adb reverse` 这条路一旦通了，改协议就是改 python，迭代最快。
2. 通了之后第一件事：抓到 `checkupdate` 的原始请求（base64(DES-ECB, key `43((zmIp`)），
   照 v800/v411 的 `LocalServer`/`Canned` 造应答，把更新检查放过去。
3. 然后看它是先要 4399/蜂鸟 登录还是先进选服。**这一步是这条路的唯一风险**：
   原包没法用 `FnForce` 伪造 SDK 登录，只能让 UC/蜂鸟 SDK 真的登录成功
   （或把它的接口也 MITM 掉）。
   - 登录链（Java）已拆清：`YJMobileJNIHelper.loginHummingbirdSDK()`
     → `SsjjFNSDK.login(activity)` → `llL1ii.onLoginSucceed(SsjjFNUser)`
     → `hummingbirdLoginFinished()`；`guestLoginHummingbirdSDK()` 是游客登录入口。
   - 如果 SDK 服务器还活着，这条路的成本就很低。

## 四之二、重大进展（本轮最后）：MITM 打通，抓到真实报文

把「重定向到本机」的最后一公里修好之后（关键是 **mangle 表把 app 的 fwmark 清 0**，
否则 REDIRECT 到 127.0.0.1 的包会被 per-uid 路由又扔回原网卡）：

```sh
adb reverse tcp:8443 tcp:8443
su -c 'sysctl -w net.ipv4.conf.all.route_localnet=1'
# 绑定挂载信任库（重启失效），把 v11/certs/c5d7d7c3.0 放进 /data/local/tmp/cac
su -c 'mount --bind /data/local/tmp/cac /system/etc/security/cacerts'
UID=$(dumpsys package com.zmxyol.union.uc | sed -n 's/.*userId=\([0-9]*\).*/\1/p' | head -1)
su -c "iptables -t mangle -A OUTPUT -p tcp -m owner --uid-owner $UID --dport 443 -j MARK --set-xmark 0x0/0xffffffff"
su -c "iptables -t nat    -A OUTPUT -p tcp -m owner --uid-owner $UID --dport 443 -j REDIRECT --to-ports 8443"
python v11/mitsrv.py            # PC 侧，记录完整请求
```

**结果：客户端信任了自签 CA，443 全量被接住。** 抓到的第一手报文：

```
GET http<path>   ← TP2 反外挂配置
POST http<path>                                   ← 更新检查
  Content-Type: application/json
  Content-Length: 1364
  -*-4399=-eDMSfv6/7Fb3e8hCNqbhOJvMqBD6K2xvimIzAJWVkejJcsH... (base64)
```

### 但 11.4.0 的加密换了

- 报文前缀变成了 `-=4399=-`（v8/v411 没有这层）。
- 用 v8 的 `DES-ECB/PKCS5, key="43((zmIp"`（`v11/des.py`）解出来是**乱码**。
- 明文 libgame 里 **搜不到** `43((zmIp`、`-=4399=-`、`yjDesEncrypt`——和 URL 一样是运行时解密的。
  → **11.4.0 换了 key 或整个编码方案**，必须重新逆。

好消息：libgame 现在能解成明文（见 §一），找 `yjDesEncrypt`/S-box/base64 表就是直接搜
`.text` 里的常量表（DES 的 8 张 S-box、或 AES 的 Te0 表），比之前只能看 dump 强得多。

## 五、一句话总结

- **能改的东西变多了**：libgame 现在可以随便打补丁（XOR 0xB5 已解）。
- **exit(15) 还没定位**，但已经排除了 guest libc 与 libgame 裸 svc，
  剩下「libtprt 裸 svc / g_tprt_pfn_array 回调」和「seccomp 验证」两个明确方向。
- **旁路已打通到「能看全量报文」**：原包 + 自签 CA + iptables 重定向 + 本地 TLS 服，
  客户端完全信任，更新检查请求已经抓到。
- **剩下的硬骨头是 11.4.0 的新编码**（`-=4399=-` 前缀 + 换了 key/算法），
  以及之后的登录链（原包不能伪造 SDK 登录，只能让 UC/蜂鸟 真的登录成功或把它也 MITM 掉）。

### 建议的下一步顺序

1. 在明文 libgame 里找新的编解码函数（搜 DES S-box / AES Te0 / base64 字母表 / `0x120` 这个 mode 常量），
   把 `-=4399=-` 那一层的算法和 key 定下来 → 就能造应答了。
2. 用本地服把更新检查放过去，看下一步要什么（登录/选服），再决定是不是要把 SDK 接口也接管。
3. 并行保留 exit(15) 那条线：把 seccomp 验证做干净（现在的构建崩在启动，需要先确认
   seccomp 真的装上：`cat /proc/<pid>/status | grep Seccomp` 应为 2）。
