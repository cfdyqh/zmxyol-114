## 一、登录不只是账号——还要实名认证

把 SDK 登录页拉下来（`v11/login_page.html`）并实际运行到那一屏之后，界面依次是：

1. 9game/7723 账号登录（通行证 + 密码，表单 POST
   `my.7723.com/cysdkfloat/user_9game.php?action=login&app_id=1847&pGameId=539817`，
   回调 `htt<path>
2. **网络游戏用户实名登记通知**（身份证 + 真实姓名 + 证件号 + 立即认证），
   截图 `v11/shot_loginform.png`

也就是说：原包 + 本地服这条路，除了要 9game 账号，还要**过实名认证**（需要真实身份证）。
这对「离线单机」来说是不可接受的依赖。

→ **结论：主攻方向切回 de-乐固 + FnForce**（伪造 `llL1ii.onLoginSucceed`，
不碰 SDK、不碰实名、不碰网络）。原包路线留作「只想玩、能接受联网登录」的备选。

## 二、Legu 的运行时函数表：能 dump，但不能直接写回去

在**乐固生效**的进程里 dump 了 libtprt 的两张表（这一步很有价值）：

| 表 | 运行时地址 | 内容 |
|---|---|---|
| `g_tprt_pfn_array` | 实测数据在 `libtprt_base + 0x24c00`（符号值 +0x100） | 3027 个字，1633 个非零；其中 34 个是 libtprt 内部的 Thumb 桩（偏移 0x668d/0x57a9/0x5935…），其余是混淆过的值 |
| `g_tprt_ori_array` | 实测在 `libtprt_base + 0x27b4c` | 438 个非零，混合（含 `_tp_` 开头的字符串碎片） |

然后做了实验：在 de-乐固包里，由我们自己的 `libtersafe2` 替身（`v11/native/tersafe2_tprtfill.c`，
带 `tprt_tables.c` 里的 12 KB 原始字节）在构造函数里把这两块**按原样写回**。

结果：**exit 码从 15 变成 7，而且死得更早**（写完 ~20 ms 就退）：

```
I/YJOffline: tprt tables: pfn=0xb33cd00 ori=0xb33fc4c
I/YJOffline: tprt tables: wrote 12108 bytes @0xb33cc00
I/YJOffline: tprt initialize -> 0
I/YJOffline: tprt release ok
I/Zygote   : Process 16498 exited cleanly (7)
```

`7` 正是 libtprt 自己那 11 个裸 `svc exit_group` 里的一个码（7/16/21/22/27/28 之一）。
→ **libtprt 对自身数据段有内存自校验**（它字符串里那个 `ch_tprt_mem` 就是干这个的），
我们一改它的表就被发现。

**所以要恢复这两张表，必须先把 `ch_tprt_mem` 这层内存校验 patch 掉。**

## 三、下一轮的具体打法（已经收敛得很窄）

1. **逆 libtprt 的内存校验 `ch_tprt_mem`**
   - 它是 libtprt 自己的函数（字符串 `ch_tprt_mem` 在 .rodata），
     `v11/ghidra/` 里已经有工程（`<path> 12.1.4 headless 可用。
   - 手法：先找 `ch_tprt_mem` 的引用（字符串在 .rodata 里有直接地址，虽然方法名是运行时解密的，
     但这个字符串是静态的），定位校验函数，把它的「发现不一致 → exit_group(code)」改成直接返回。
   - libtprt 的 11 个裸 `svc` 地址已经列在 `v11/交接_11.4.0_第2轮.md` §2.3，
     定位到校验点后直接改判断即可。
2. 校验 patch 掉之后，再用 `tersafe2_tprtfill.c` 把两张表写回去 → 看 exit(15) 是否消失。
3. 同时把 `v11/java/.../LocalServer` 的编解码从 v8 的 `43((zmIp` 换成
   11.4.0 的 `1#(z1Rr>` + `-=4399=-`（`v11/codec.py` 是参考实现），
   这样过了 exit(15) 之后本地服立刻能听懂客户端。

## 四、本轮又试掉的两个假设（都记下来，别再重复）

**A. 字符串 xref 找 `ch_tprt_mem` 的校验函数 —— 走不通**
Ghidra 里 9 处 `ch_tprt_mem` 字符串（Ghidra 地址 0x3415c/0x34410/0x34ecc/…）**没有任何 xref**，
和主字符串池一样是通过运行时填充的指针表访问的。→ 静态 xref 这条路要在解出
`FUN_0001ceb4`（JNI_OnLoad 里那个字符串解密器）之后才走得通。

**B. seccomp `SECCOMP_RET_TRAP` + SIGSYS 抓 exit —— 破坏性，没拿到信息**
`v11/native/exit_trap.c`：`prctl(PR_SET_NO_NEW_PRIVS)` + `prctl(PR_SET_SECCOMP, FILTER)`
（用 prctl 而不是 `syscall(__NR_seccomp)`，避开之前 hook 吞 syscall 的坑），
对 nr∈{1,248,252} 返回 TRAP。安装成功（`prctl(SET_SECCOMP) -> 0`），但进程在
**Boot.start 之前就死了**，SIGSYS 处理器一次都没跑；反复重启还把模拟器拖崩了
（system_server 掉线，必须 `ldconsole launch --index 0` 重启，约 45 s）。
→ 这条路在 houdini 上不可用，别再用 TRAP 型 seccomp。

**C. libtprt 那 11 个 exit 裸 svc 没有直接 `bl` 调用者**
扫了 libtprt 全 `.text`（Thumb）找 `bl/b.w` 到 0x2bd4/0x2eb8/…/0x11d74，**一个都没有**。
说明它们是**函数内联的尾部退出序列**（`push {r4,lr}; movs r0,#code; push {r7};
movs r7,#0xf8; svc #0`），要定位所在函数得**从 svc 往前**找函数起点，
或者直接用 Ghidra 查「包含该地址的函数」：
```
site 0x2bd4 -> Ghidra 0x12bd4 ; 0x2eb8 -> 0x12eb8 ; 0xcdf8 -> 0x1cdf8 ...
```
下一轮就从这里进：把这 11 个地址所在的函数逐个 decompile，看哪个是
「文件/内存完整性校验 → 退出」。
